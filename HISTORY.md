## 2026-07-28
Made a failing chat tool degrade to one bad answer instead of a stalled conversation. `EventsTool.invoke()` assumed every available event carries a `summary`, but an event is `status: "available"` from capture while `summary` is written by a later processing pass, so a recently captured event threw on `event.summary.seconds`; it now reads through a `{}` default and routes `begin`/`end` through a `toDate()` helper tolerating a Firestore Timestamp, a plain Date, or nothing, and still reports unsummarized events rather than hiding them from the model. The crash was survivable in principle but wasn't: `ToolBox.invokeAll()` used `Promise.all`, so one thrown tool rejected the batch, no outputs were posted for *any* `call_id` in that turn, and the conversation waited forever on a `function_call_output` that could never arrive. It now uses `Promise.allSettled` and emits `{error}` for the failing call only, with the result formatters wrapped per call (rolling back a partial message/output so one call still yields one of each). Fixed the shapes that crashed those formatters on the same path: `isRows()` threw on a null result and on an empty array (`Object.values(result[0])`), and `addObjectResult()` threw on undefined because `JSON.stringify(undefined)` is `undefined`, not a string — a tool returning nothing now reports `null` rather than being misreported as a failure. Locked in by a new `tests/e2e/toolbox.e2e.mjs` (`npm run e2e:tools`, also added to `npm run e2e`) that drives the real `ToolBox` with stubbed results across seven shapes — rows, a thrower, an empty list, undefined, null, a plain object, and a circular structure — plus an unknown tool name and the `events_list` unsummarized-event case; reverting either fix takes it from 15/15 to 0/9, the run dying before the events section exactly as the batch rejection did in production.

## 2026-07-22
Added `src/viz/crowdMap.js` (x002 — milestone 1 of the chat crowd-sentiment banner): a top-down ballpark map that plots approximate crowd-member positions, colored by sentiment, inside each camera's field-of-view wedge. Built and validated standalone first; **no shipping source file was modified** beyond a one-line entry added to `rollup.config.js`. The viz reuses the 5 FOV triangles, labels, `raimondi-seat-map.png`, and `scoreToHue()` from `src/viz/cameramap.js`, and mirrors the softmax-weighted emotion scorer from `Score.computeRowScore()` plus the `defaultEmotionWeights` table from `src/data/profiles.js`. Both are **copied rather than imported** — `scoring.js` and `profiles.js` construct firebase-backed singletons at module load (`database = new Database()`, `profilesData = new ProfilesData()` which fires `getById()` on construction), so importing either would drag Firestore into a standalone canvas; unify into a shared `stadiumGeometry.js` when the viz graduates. The core new idea is a pseudo-projection from 4K camera-image space to top-down map space, since **no homography or ground-plane calibration exists anywhere in the codebase** and true seat placement is therefore impossible: each triangle gains an apex vertex (the camera lens, where the FOV converges), the opposite edge becomes the far base, and a detection is placed bilinearly with depth `t` derived from box height (taller box = closer face = nearer the apex) and lateral `u` from the box centre x over a 3840px frame — `P = lerp(lerp(A,B1,t), lerp(A,B2,t), u)`. This is impressionistic, not survey-grade: box height is a confounded depth cue (zoom, adult vs child). `APEX_INDEX = [0,1,0,0,0]` is seeded by the heuristic "vertex nearest that camera's label" (labels sit on the camera marker in cameramap) and is the most likely thing to need flipping per wedge. Depth constants `H_NEAR=150`/`H_FAR=35` bracket the box-height range actually observed in the sample files (26–154px); the first guess of 140/70 clamped every face under 70px onto the far base edge. Data reaches the viz imperatively via `setDetections(camera, rows)` and `setAllDetections({1: rowsA, 2: rowsB, …})` — deliberately no eventBus/summarizer coupling this milestone — with the batch form being the exact shape the eventual chat tool will feed 5 independent per-camera streams through. Dev harness at `public/explore/crowdmap.html` + `src/crowdmaptest.js` (new rollup entry `crowdmaptest`), following the `public/explore/synthetic-smoke.*` precedent: nginx serves `public/explore/*` statically because `explore` isn't in the proxy regex, so the page needs no route. It preloads both `samples/expressions-*.json` (copied into `public/explore/`, since repo `samples/` is not served), groups detections by frame, and offers a dataset toggle, a wedge selector, and a time scrubber; "all 5 wedges" assigns the two samples to different cameras so the wedges render genuinely independent data rather than one mirrored stream. Verification against the real samples: 100% of projected boxes land inside their wedge (bilinear placement guarantees it — confirms no coordinate bug, not realism), and camera 5 shows the expected dead zones over the concession stands. Noted but not addressed: with the current profile weights `calm-few` scores a *higher* mean sentiment (63) than `cheering-many` (40), opposite to the dataset names — both samples are dominated by zero-weighted emotions, so this is a weight-table question rather than a viz defect. Still deferred: `stadiumGeometry.js` extraction and the CameraMap refactor, the `CrowdSnapshotTool` chat function + `ui.showCrowdSnapshot` event, the `rschat.js` banner mount, and live playback sync.

## 2026-07-16
Reworked Synthetic View (x001) to render only pipeline silhouettes, over a background plate, with interpolated motion — and found and fixed the pipeline bug that had made the whole view meaningless (`docs/x001-silhouette-association-bug.md`). **The data bug came first and explains the rest:** each expressions row shipped a face detection and a body outline that *were different people*, re-rolled every frame, so the view drew each person's body tinted by an unrelated person's emotion. Diagnosis was geometric — only 24.8% of faces fell inside their own row's silhouette, and for a given `person` track between consecutive frames the face box moved 4.1px median while its silhouette moved 947.5px. Fixed pipeline-side (outlines were only being produced for people needing neighbor removal, then attached to arbitrary rows); re-processed `vy:video:coke` now measures 99.7% containment, 17.3px silhouette movement, and 0% `person` teleports (was 14.1%), with new `person_box`, `face_confidence`, `frame_idx`, and a top-level `tracks[]` re-id signature array. **Renderer** (`src/viz/syntheticView.js`): dropped the procedural face-glyph path entirely (`PRESETS`, `blendParams()`, `drawFace()`, size constants) — silhouettes are the only representation now, and boxes without one are skipped; moved the remaining module-level helpers into the class to match `heatmap.js`; `backgroundForScore()` → `colorsForScore()` (the `fg`/`mouthFill` fields existed only for facial features). Added an optional "clean plate" background — a people-free frame from the same camera — composited under the silhouettes so they sit in the real scene; its URL is derived with no new metadata, as a sibling of the expressions JSON (whose resolved storage endpoint now rides along on the `scoring.video` event via a new `url` field) named `background-${hierarchy}.jpg`, mirroring the existing `summary-${hierarchy}.json` convention; it's downscaled once into an offscreen canvas rather than rescaling a 4K jpg per frame. Replaced `playback.timeupdate`-driven painting (~4Hz — the view *replaces* the video rather than overlaying it, so it was effectively a 4fps slideshow) with a `requestAnimationFrame` loop that runs only while visible and playing. Outlines are now interpolated rather than snapped: `Score.linkSilhouetteChain()` does one O(n) backward pass at load linking each row to the next row of the same person that actually carries an outline (`row.nextSilhouetteRow`), and `windowBoxes` passes the originating row through to `ActiveBoxManager` as `silhouetteRow`, sticky alongside the outline itself. `_shapeFor()` walks that chain to whichever detection pair brackets the current video time and lerps across exactly the real interval — read-ahead rather than a render delay, so zero lag, and exact pacing where a fixed easing constant could not work (gaps run p50 0.33s, p90 1.0s, p99 6.7s, so any constant finishes early and sits: visible lerp-pause-lerp). The renderer must walk the chain itself rather than be handed a fixed pair: the box is only rebuilt on the ~4Hz timeupdate tick while the loop draws at 60fps, so a handed-over pair goes stale between ticks and every shape reached its target and froze until the next tick — and 250ms against the 333ms detection cadence beats at exactly 1s, so the whole crowd stuttered about once a second. Replaying the real chunk through `ActiveBoxManager` at the 4Hz tick and `_shapeFor()` at 60fps measures frozen frames dropping from 21% to 2% once the renderer walks on its own clock. `_alignRotation()` fixes vertex correspondence first — the outlines are a consistently-wound contour walk whose *starting point* drifts, so identity vertex mapping is best only 34.5% of the time and lerping without it drags vertices around the contour; aligning cuts per-vertex displacement p50 49.1→36.4px and p90 153.7→95.5px. A 4Hz clock can't drive 60fps interpolation, so `_videoTime()` extrapolates between `timeupdate` samples with the wall clock. **Tracking** (`src/scoring/`): `Tracker._namespaceChunkIds()` shifts each chunk's pass-through `person` ids into a disjoint range drawn from the same counter `_assignByIoU()` uses — chunks are processed in parallel so ids are only unique *within* a chunk, and `ActiveBoxManager` would otherwise match chunk 2's "person 5" to chunk 1's and teleport the track; memoized per chunk so a seek reproduces the same ids, first chunk gets offset 0. `ActiveBoxManager.update()` now runs two passes — identity, then handoff — with `refreshBox()`/`createBox()` extracted. The handoff exists because `matches()` treats two distinct ids as two people, which is right when both are seen at once but wrong when a track breaks and re-acquires (certain at every chunk boundary): an unclaimed row overlapping an unclaimed box is adopted, via `findHandoffCandidate()` picking nearest-centre rather than first-found. The two passes are load-bearing — interleaved, a new track's early row could adopt an established box whose own row hadn't been reached yet, cascading into continuous identity churn every tick, since the caller replays the whole 3s window per tick. Fixed the sticky-field guards: they tested `!== undefined`, but the pipeline signals "couldn't compute" with an explicit `null` (as `pose` has always done), so the "sticky last-known silhouette" behavior described in the 2026-05-06 entry had in fact never worked; `hasValue()`/`hasSilhouetteData()` now treat null, absent, and empty-array alike. Also reset `markedAsLost` on refresh (a recovering track could previously only ever count as lost once — inert today since all three volatility factors are 0.0, but it would skew `lostVolatility` the moment they're enabled). No fade: an earlier attempt keyed on time-since-detection, which dimmed the *entire* crowd in unison during a chunk load stall; shapes hold while their track is alive and drop on expiry. Scoring output is unchanged throughout — `person` ids are opaque, and volatility (the only path from box churn to `currentScore`) is gated behind zeroed factors.

## 2026-05-05
Added an exploratory "Synthetic View" toggle to the reports player (x001 — see `docs/x001-synthetic-view.md`). When enabled, the `<video>` element and the heatmap overlay are hidden, and a 2D canvas renders a per-face procedural face glyph at every active face box, with the glyph's expression driven by the face's emotion vector. The new module `src/viz/syntheticView.js` mirrors the lifecycle pattern of `src/viz/heatmap.js` (singleton class, eventBus subscriptions to `playback.timeupdate` / `ui.hierarchyChanged`, paint pulled from `activeBoxManager.get()`, same 3840×2160 → 1280×720 scaling). Each face is composed of canvas primitives — circle (color-tinted), two ellipses for eyes, two short tilted line segments for eyebrows, and a quadratic Bezier for the mouth — parameterized by 7 numeric properties (`eyeOpen`, `browTilt`, `browY`, `mouthCurve`, `mouthOpen`, `mouthW`, RGB `tint`). Per-face params are a weighted blend of preset values for the top-3 cores from the box's `cores` map (threaded through from `src/scoring/scoring.js` `windowBoxes`), normalized to sum=1; `tint` blends per-channel. Disgust + Fear get their own preset rows rather than VRM-style preset blends. The toggle wiring is in `Reports.toggleSynthetic()` in `src/rsreports.js`. The renderer is canvas-only with no WebGL, no async init, no VRM dependency — drawing 60 faces is a few hundred 2D primitive calls per timeupdate, well under any perf budget. The first iteration of this exploration tried VRM 1.0 head meshes via `@pixiv/three-vrm`; that approach passed its standalone smoke test (60fps at 60 instances) but had unacceptable runtime cost in the integrated reports player (timeupdate cadence + main-thread contention with video.js, scoring, charts) and was visually obscured by the heatmap overlay. The procedural pivot drops both problems. The VRM smoke test at `public/explore/synthetic-smoke.html` is kept for parallel exploration of head-only VRoid models / a possible pre-rendered-PNG fallback if procedural reads as insufficiently expressive at production face-box scale (~33 px). `three` and `@pixiv/three-vrm` deps remain in `package.json` for that smoke-test path; they are not imported from any runtime module.
