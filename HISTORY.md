# Change History

## 2026-04-28
Ported the H017 score-smoothing transform from the model-improvment repo into the scoring stack. Two passes: (1) `Summarizer.smoothSummary()` in `src/scoring/summarizer.js` applies a causal rolling-mean (window=10 buckets, configurable via `smoothWindow` / `smoothMode`) to the per-second bucket `score` field after the existing max-aggregation — this is the H017-validated path that recovered ~67% of the lost API↔local Pearson r (mean r 0.30 → 0.508) on the 4 critical-event probes. (2) `Score.updateCurrentFromWindow()` in `src/scoring/scoring.js` adds an independent causal rolling-mean (window=40 ticks ≈ 10s) on `currentScore` for the live-UI dial; gated by `Score.liveSmoothEnabled` so `Summarizer.create()` toggles it off via try/finally during offline rebuild and the summarizer always sees raw post-volatility `currentScore` (preserving the H017 max-then-smooth math). The live-smooth buffer is reset in `resetWindow()` and `handleTimeSeek()` to avoid stale lookback bleeding across seeks. `count`, `maxScore`, `people`, and time fields pass through unchanged. Setting `smoothWindow<=1` / `smoothMode="none"` (summarizer) and `liveSmoothWindow<=1` (Score) restores byte-identical pre-change behavior. See `docs/H017-smoothing-scores.md` for the full handoff and validation procedure.

## 2026-04-23
Added Microsoft as a federated sign-in provider alongside Google, and wired up account linking so a user whose email is already registered under one federated provider can add the other without creating a duplicate account. The sign-in card in `src/rsauth.js` now shows Google → Microsoft → "or" → Enterprise email/password. On `auth/account-exists-with-different-credential`, the pending credential and email are stashed, `fetchSignInMethodsForEmail` identifies the existing provider, and the sign-in card is swapped for a "Link your accounts" card that re-runs sign-in with the existing provider then calls `linkWithCredential` to attach the new credential. Linking is supported between Google and Microsoft; if the existing method is `password` the linking card falls back to a "please sign in using that method" message (full password-linking flow is deferred since Business sign-in is gated to contract customers). Microsoft provider requires an Entra app registration (client id + secret) configured in the Firebase console.

## 2026-04-23
Enabled Stripe Tax on credit-pack purchases. The `/api/billing/checkout/create` handler in `src/functions/billing/index.js` now sets `automatic_tax: { enabled: true }`, `billing_address_collection: "required"` (Stripe needs an address to determine jurisdiction), and `tax_id_collection: { enabled: true }` (lets B2B customers enter a VAT / tax ID for reverse-charge treatment where applicable). Credits granted on `checkout.session.completed` are still the pack amount — tax is added on top of the pack price and charged to the customer, not deducted from credits. UI: the pack card in `src/rsbilling.js` now shows a muted "Plus applicable tax at checkout" line under the price so the post-tax total on Stripe Checkout isn't a surprise. **Stripe Dashboard steps required before deploy:** (1) enable Stripe Tax and register in the relevant jurisdictions; (2) set the tax code on the credit-pack **Product** to `txcd_10105004` ("Artificial Intelligence as a Service" — prepaid digital services). The tax code lives on the Product, not the Price, so it applies to all future price rotations automatically.

## 2026-04-22
Changed `POST /api/file/upload/:path` to `POST /api/file/upload` with `path` in the JSON body. The URL-segment form was incompatible with Firebase Hosting / GCLB, which decodes `%2F` before forwarding to the function — so a frontend-encoded path like `videos%2Fcombined2.mp4` arrived at express as two segments and missed the `/upload/:path` route, returning 404. Body-based path also avoids the encode/decode dance entirely. Updated `src/data/storage.js::requestUploadUrl` to send `{ path, storage, mimeType, oid }` and `src/functions/file/index.js` `/upload` handler to read `path` from `req.body`. Breaking API change, but the endpoint has no external callers yet.

## 2026-04-22
When an organization's credit balance is increased, any `jobs` docs matching that `oid` with `status: "rejected"` are automatically reset to `status: "requested"` so credit-gated refusals retry on the processing side. For each reset job whose `refType === "file"`, the corresponding `files/{refId}` doc is also compare-and-swapped from `status: "rejected"` → `"processing"` (via `database.atomicUpdate`, so a file that's already moved past "rejected" is left alone). The reset runs after the balance transaction commits (Firestore transactions can't run collection queries). It's wired into both credit-add paths: `grantCredits` in `src/data/creditGrants.js` (admin grants, future system grants) — only when the transaction actually applied and `amount > 0` — and the Stripe `checkout.session.completed` handler in `src/functions/billing/index.js`, gated on the stripe_events idempotency transaction returning `true`. New helper `JobsData.resetRejectedByOrg(oid)` in `src/data/jobs.js`.

## 2026-04-21
Introduced an explicit `status` field on file documents — `"available" | "deleted" | "processing" | "failed"` (with `"rejected"` reserved for credit-gated refusals). Status replaces the old `deleteRequested` timestamp (legacy docs are still honored via an `effectiveStatus` helper that treats missing `status` as `"available"` and a set `deleteRequested` as `"deleted"`). `FilesData.save` now takes a trailing `extras` object carrying optional `{ status, size, duration, creationTime }`, and the Uploads flow records `size` from `File.size` at upload time plus `status: "processing"` for types that request server-side processing. `src/functions/file/index.js` `/delete/:file_id` now writes `status: "deleted"` (and a `deletedAt` ms timestamp). Server-side processing code is responsible for transitioning `processing` → `available` / `failed` / `rejected` and for populating `duration` / `creationTime` metadata. The Uploads view now uses a real-time Firestore query listener (`database.listen`) instead of a one-shot `getByContext`, so lifecycle changes surface without a manual refresh. UI: per-row status badges (color-coded with a spinner for processing), size and duration columns, "uploaded X ago" via `timeUtil.formatTimeAgo`, filename linked to `/reports/{hierarchy-slash-separated}` (derived from the existing `hierarchy` field via `Hierarchy.toFileString("/")`) when the file is `"available"`, `confirm()` on delete, and hide-deleted-by-default with a `Show deleted (N)` toggle. Reports → Videos selector now also uses the live listener and only surfaces `"available"` videos.

## 2026-04-20
New users now receive a one-time welcome grant of 1,000 free credits (≈ 100 minutes of processing) when their personal organization is first created. The grant is written in the `/api/org/create/personal` handler via a new shared helper `src/data/creditGrants.js::grantCredits`, which runs the balance + ledger Firestore transaction used by both admin grants and the Stripe webhook. The helper's `onlyIfNew: true` option gates on the absence of a `credit_balances/{oid}` doc so the welcome grant is naturally idempotent — repeated `/create/personal` calls for an existing personal org do not re-grant. The `/admin/grant` route in the billing function was refactored to use the same helper. Ledger rows for the welcome bonus are `type: "grant"`, `source: "system"`, `ref: "welcome"`. Existing users who already have a personal org will not be auto-backfilled; use the admin grant UI to give them the bonus manually.

## 2026-04-20
Added admin credit grants. `/admin` is now gated — owners of the Vy admin org (id set via the `VY_ADMIN_OID` env var, default `00hB8gSxKMs5SSLCCbyi`) see the existing jobs chart plus a new "Grant credits" section with a search box (org name / org id / user email) and a per-result grant form. Non-admins see an "Admin access required" message. Server-side: `requireAdmin` in the billing function checks the caller against the admin org's `owners` array and gates three new routes — `GET /api/billing/admin/status` (open to any authenticated user, returns `{isAdmin}`), `GET /api/billing/admin/search?q=...` (org substring match in memory + exact-id + email-to-user lookup via `firebase-admin/auth`), and `POST /api/billing/admin/grant` (runs a Firestore transaction that writes a `grant`/`adjustment` ledger row with `source: "admin"` and updates `credit_balances/{oid}`, mirroring the Stripe webhook path). Negative amounts produce an `adjustment` row so admins can claw back mistaken grants.

## 2026-04-20
Added Stripe-backed credits billing. New top-level `/billing` tab (promoted out of the stubbed Settings tab) where org owners see their current balance, buy credit packs via Stripe Checkout (hosted, redirect flow), and view an activity feed that interleaves purchases with usage debits written by the processing service. Credits live in their own collections — `credit_balances/{oid}` for the running balance and `credit_ledger/{id}` for the append-only log — so the existing `organizations` rules stay untouched. New `billing` Cloud Function exposes `/api/billing/packs`, `/checkout/create`, `/balance`, `/history`, plus a raw-body `/webhook/stripe` that verifies the signature and runs a Firestore transaction (balance + ledger + `stripe_events/{id}` idempotency guard) on `checkout.session.completed`. Owner-only gating enforced in both the UI and the function. Deduction and insufficient-credit rejection remain the processing service's responsibility; the billing function never writes debits. Initial pack: 1,000 credits for $10 (1¢ per credit = 10 credits / min at $0.10 / min). Stripe `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, and `STRIPE_PRICE_STARTER_1000` provided via `defineSecret`.

## 2026-04-13
Follow-up on the TLA fix: reverted `vanjs-core` to a static import in `src/data/orgContext.js` and restored eager `van.state` field creation in the `BrowserOrgContext` constructor. The lazy load introduced a race — `src/ui/topbar.js` builds its DOM synchronously at module load (via `rsnav` → `nav.addElements()` → `topBar.addElements()`) and reads `orgContext.currentOrg.val` / `userOrgs.val` / `isLoading.val` / `currentOrgId.val` inside van render closures, which would crash reading `.val` of `null` before auth fired `orgContext.init(user)`. vanjs-core is safe to module-load in Node (no DOM side-effects), so the server v1 bundle tolerates it. `ServerOrgContext` still lazy-loads `node:async_hooks` to keep the module graph free of top-level await.

## 2026-04-13
Fixed `ERR_REQUIRE_ASYNC_MODULE` on Firebase Functions deploy. `src/data/orgContext.js` had top-level `await import(...)` for `vanjs-core` / `node:async_hooks`, which rollup preserved as TLA in the v1 bundle and broke Firebase's `require()`-based function loader. Moved both imports to lazy loads inside `BrowserOrgContext.init()` and `ServerOrgContext.run()` (via a new `_ensureAls()` helper), deferring reactive-state and `AsyncLocalStorage` instantiation to first use. `orgContext.run()` is now async, so `src/functions/v1/middleware.js` awaits it.
